## Decision

The supplied manual is not ready to serve as an implementation contract. Its strongest gaps are architectural: a conforming implementation can use a stale judgment, leak through handle metadata, release after a deletion acknowledgement, or delete a redacted replacement along with its original. Its literal grounding rule also confuses the presence of a value with authorized use of that value. These are blockers, not editorial preferences.

The refined manual repairs the identified contracts in their owning sections and restores proposal requirements lost in formalization. The user subsequently selected Codex/OpenAI first, Claude second, and delegated configurable retention and initial missing-detail choices. The candidate now supplies those choices, a complete delivery plan and 20 discriminating acceptance scenarios.

**Do not deem the revised candidate unconditionally implementation-ready yet.** Codex's documented hook coverage does not establish the complete mediation and exact submitted-context capture required by the instrumented profile. Concrete storage/backup recovery evidence and independent review of the revised bytes also remain outstanding. A useful memory-service integration and the full instrumented adapter are separate delivery boundaries; passing the former cannot be reported as passing the latter.

No accepted-current D3 was supplied. The defects below meet the substantive threshold for a **Serious Challenge if the affected claims are asserted as accepted guarantees**. Here they are recorded as blocking challenges to proposed D3; this review does not invent an accepted authority or claim to have reopened one.

## Codex-specific finding added by the user's runtime choice

**F18 — Runtime feasibility remains unverified; D3 integration boundary.** The user chose Codex as the first runtime. Official documentation states that local tool hooks omit hosted tools, some specialized paths can opt out, and continuing an existing exec session does not repeat its pre-tool hook. It explicitly warns against treating hooks as complete enforcement. This is a concrete obstacle to equating an MCP/hook integration with the instrumented profile. [Official Hooks documentation](https://learn.chatgpt.com/docs/hooks).

The app-server documents threads, turns, events, approvals and compaction notifications. Those interfaces are useful integration evidence, but they do not by themselves establish a complete sealed model-input stream or universal pre-release interception. MCP supplies a supported memory tool surface. The conclusion that full UPMS instrumentation still needs a feasibility demonstration is this reviewer's inference, not a vendor claim that every possible integration is impossible. [App server](https://learn.chatgpt.com/docs/app-server), [MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).

**Disposition:** candidate 14.1 targets Codex memory-service integration first and explicitly gates full instrumentation. Discriminating evidence: a pinned adapter demonstrates pre-provider capture, compaction/resume/reset, all enabled tools and subagents, provider disclosures, and blocking output before display/release. Any uncovered route must be disabled or the stronger profile withheld. A future Claude adapter needs its own evidence. No claim is made that choosing another OpenAI model resolves a harness boundary.

## Bounded challenge and simplification pass

The out-of-matrix question was: can each component obey its local rule while the system violates correction, confidentiality or retention? F01, F05, F06 and F07 are concrete surviving traces in the baseline. These do not depend on a poor embedding model or an unusual workload; they concern the specified semantic boundaries.

Architectural alternatives considered qualitatively:

| Choice | Selected candidate and cost | Rejected/deferred alternative |
| --- | --- | --- |
| New-evidence freshness | Per-scope evidence epoch; simple exact invalidation, potentially excessive reassessment | Row-only validation is inadequate; narrow predicate tracking deferred until completeness is specified/tested |
| Handle isolation | Fixed-slot exception with conservative default taint; less planner flexibility | Arbitrary metadata advertised as harmless is unsafe; removing handles entirely remains viable if the runtime cannot enforce them |
| Release/barrier ordering | One core-owned gate/fence; extra latency and availability coupling | Check-then-send leaves the race; async invalidation is not enforcement |
| Erasure | Prompt live purge plus finite encrypted-backup expiry; explicit completion delay | Immediate per-unit crypto-erasure not claimed without a concrete key/copy proof |
| Delivery | Useful memory-service first, separately qualified instrumented adapter | Calling MCP/hooks full instrumentation would overstate coverage |
| Knowledge structure | Keep Event/Claim/Judgment identities, instantiate claims lazily | Mandatory exhaustive extraction before recall adds cost; collapsing assessments into sources loses revision meaning |

Removed duplicated hypothesis truth ownership, corrected overdue handling and kept ordinary storage/outbox/adjacency structures. No second authority registry, universal confidence scorer, event bus or mandatory graph database was added. Additional contracts describe obligations at existing owners, not new standalone services.

The refined candidate was self-checked against the traces and for interaction defects. This uncovered and repaired replay-copy expiry versus canonical-source expiry and raw consistency-counter disclosure. No independent acceptance or exhaustive security proof follows from this self-check. No runtime experiment compared these architectures.

## Defaults, status and actual remaining work

The user delegated initial choices, so the revised manual does not leave every parameter as an unanswered question. The pilot defaults include 5 users/10 sessions, 100,000 live events, 180-day raw retention, a 7-day reconstruction-copy window, 7-day backup expiry, a 24-hour live-purge target and an 8-day complete-purge target. All are configurable agent choices, not measured or externally mandated values. Source/dependency retention takes precedence over convenient derived-record lifetimes. Complete-within-scope is never reported merely because a target deadline elapsed.

The full binding table is candidate 14.2. It also sets bounded processing/search/context budgets, conservative action/admission policy, a 5-minute maximum assessment age plus exact evidence-epoch checks, and recovery targets. Exact processor/account/category permissions stay deny-by-default until configured; the user's vendor preference is not blanket permission to disclose all future memory.

Remaining closure is limited and concrete:

1. **Independent D3 falsification of the revised candidate and product acceptance.** This report cannot independently approve text its author just wrote.
2. **Codex instrumented-boundary feasibility.** Demonstrate the required hooks/enforcement or revise that implementation boundary. The current evidence supports a memory-service target, not the complete runtime guarantee.
3. **Storage/KMS/backup implementation binding and feasibility.** Inventory actual copies, verify key/cache/expiry behavior, and show restore cannot serve without current deletion controls. Numeric defaults are not evidence that a chosen deployment meets them.
4. **Freeze executable evaluation inputs.** The candidate supplies a synthetic evaluation design and thresholds. Actual corpus/rubric/harness/model identities and repetition/randomness choices must be fixed before measurement. No private real-session access is assumed.
5. **Resolve the historical review dependency.** The proposal and manual are available; the earlier cited architecture review and any acceptance record are not. Supply that record if it still governs, or explicitly supersede the dependency. This does not prevent reading/designing the supplied draft; it prevents claiming complete historical acceptance reconciliation.

Concrete schemas, helper functions, UI layout, language, exact model choice and storage products remain delegated D4 space where they preserve the accepted contracts. They are not all new architecture blockers. A bounded Slice 1a specification can follow acceptance of that boundary; full implementation-ready status must name which slice and profile it covers.
